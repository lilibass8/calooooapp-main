CalorieSnap Project Report
==========================

1. General Project Information
------------------------------
Project Name:
CalorieSnap

Project Type:
A mobile and web application built with Expo and React Native for meal logging and daily calorie tracking.

Current Version:
1.0.0

Short Description:
CalorieSnap is designed to help users record daily meals, save meal photos, estimate calories in a guided way, and monitor their daily calorie goal through a modern Arabic-first user interface.


2. Project Idea
---------------
The core idea of the project is to build a practical and user-friendly nutrition tracking app. Instead of forcing the user to calculate everything manually from the beginning, the app provides a simple visual workflow:

- The user enters basic profile data once.
- The user takes a photo of a meal.
- The user selects the meal type and portion size.
- The app provides a reasonable calorie estimate.
- The meal is saved to history.
- The user can review daily progress and past meals.

The current version does not claim to have real computer vision or automatic food recognition. Instead, it uses a conservative and transparent workflow that prevents fake calorie results by requiring the user to confirm that the image is actually food and then choose the category and size.


3. Problem the Project Solves
-----------------------------
Many calorie tracking apps are:

- crowded and hard to use,
- heavily dependent on long manual text input,
- based on repeated food database searches,
- or misleading when they claim to estimate calories automatically without accuracy.

CalorieSnap attempts to solve these problems by offering:

- an Arabic-first experience,
- a clear scanning workflow,
- protection against obviously wrong results such as assigning calories to a key or an object,
- a guided calorie estimation flow instead of fake AI,
- local storage with optional Supabase sync.


4. Project Goals
----------------
The main goals of the project are:

- simplify daily meal logging,
- improve visibility of the user's calorie goal,
- present meal history in a clear visual way,
- provide a codebase that can be extended later with real AI, authentication, notifications, and analytics.


5. Target Audience
------------------
The target audience includes:

- users who want an easy way to track calories,
- Arabic-speaking users who prefer a localized UI,
- people who want fast meal logging without repeated manual search,
- users who want a lightweight app that can run on mobile and web.


6. Current Solution Approach
----------------------------
The current solution is based on the principle of "ease of use with honest constraints".

Instead of pretending to analyze the image using non-existent AI, the app uses a guided workflow:

1. The user takes a picture.
2. The app shows a review screen.
3. The user confirms whether the image contains edible food.
4. If it is not food, calorie counting is rejected.
5. If it is food, the user selects a meal category.
6. The user selects a portion size.
7. The app generates a calorie estimate from a fixed matrix.
8. The user can manually adjust the number before saving.

This makes the system more honest, more stable, and much less likely to produce nonsense results.

10. Technical Architecture
--------------------------
The app uses a state-driven front-end architecture with two data sources:

Source 1:
Local storage through AsyncStorage

Source 2:
Optional cloud sync through Supabase

How it works:

- AppContext loads the global state when the app starts.
- A device-specific profile ID is created if it does not already exist.
- If Supabase environment variables are available, the app attempts to fetch remote data.
- If remote sync fails or is unavailable, the app falls back to local storage.
- Meals are always saved locally, and optionally synced to Supabase with image upload.

This architecture provides:

- partial offline capability,
- optional cloud persistence,
- flexibility for future growth.


11. Application Data Flow
-------------------------
General app flow:

1. The user opens the app.
2. Global state and profile are loaded.
3. If no user exists, the app redirects to onboarding.

   - the camera takes a photo,

13. Meal Categories and Calorie Estimation
------------------------------------------
The project uses a fixed calorie matrix based on meal category and portion size.

Current categories:

- cooked meal
- sandwich or burger
- pizza or pastry
- salad
- dessert
- drink
- fruit or snack

Portions:

- small
- medium
- large

Estimation logic:

- When a category and portion are selected, calories are retrieved from a fixed matrix in calorieEstimator.
- If the user edits the result manually, the estimation source becomes manual-adjustment.
- If an older meal comes from an older schema, it is treated as legacy.


14. Database and Cloud Storage
------------------------------
The project uses Supabase when the following environment variables are provided:

- EXPO_PUBLIC_SUPABASE_URL
- EXPO_PUBLIC_SUPABASE_ANON_KEY
- EXPO_PUBLIC_SUPABASE_BUCKET

Main database tables:

1. profiles
- stores basic user profile data.

2. settings
- stores general user settings.

3. meals
- stores meals, calories, images, category, portion, and estimation source.

Storage:
- a bucket named meal-images is used for uploaded meal images.

Security:
- Row Level Security is enabled.
- Current policies are intentionally permissive because the project is still using a bootstrap model without real authentication.


15. Local Storage
-----------------
The app uses AsyncStorage to store:

- user profile data,
- meal records,
- settings,
- last daily reset date,
- device-specific profile ID.

Important behavior:
- The project no longer deletes the entire meal history every day.
- Instead, it keeps the full meal archive and derives "today meals" at render time.

1. No fake AI
- Random calorie generation was removed and replaced with explicit guided logic.

20. Current Limitations
-----------------------
The project still has some limitations:

1. No real image AI
- The app does not automatically detect food from the image.

2. No real authentication
- It relies on a generated device profile ID.

3. Dark mode is not implemented as a real active experience
- The current UI is intentionally focused on the light theme.

4. Notifications are not implemented
- There is no working notification system yet.

5. Calorie estimation is approximate
- It is based on a fixed matrix, not real nutrition analysis.

6. On web, camera behavior depends on browser support, HTTPS, and permissions.


21. Challenges Addressed by the Project
---------------------------------------
The project addresses several technical and product challenges:

- how to make meal logging fast and simple,

- how to build a polished Arabic experience without overcomplicating the app,
- how to preserve full history while calculating daily-only statistics.


22. How the "a key has calories" Problem Was Solved
---------------------------------------------------
This is one of the most important improvements in the project.

In the older version, the app could produce a random calorie number regardless of what the image contained.

In the current version, this was solved by:

- removing random calorie generation entirely,
- disconnecting calories from the photo alone,
- adding an explicit decision step asking whether the image is food,
- stopping the flow if the item is not edible,
- showing no calories in that case,
- preventing the item from being saved as a meal.

This makes the logic much more reliable and much more honest.
